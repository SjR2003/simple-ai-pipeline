# AI Training Pipeline (Config-Driven • Versioned • MLflow-Tracked)

A modular, config-driven machine learning pipeline built for **one-click training** with a strong focus on:
**reproducibility**, **traceability**, and **extensibility**.

The pipeline supports both **end-to-end runs** and **step-by-step execution**, while logging **configs, metrics, artifacts, models, dataset lineage, and code version info** to **MLflow**.

> Built as a university project with an industry-first mindset.

---

## Key Features

- **One-click execution** (CLI runner)
- **Step-by-step execution** by editing `configs/master_config.yaml`
- **Stateful chaining**: each task consumes the previous task output
- **MLflow Tracking**:
  - params, metrics, artifacts, models
  - **auto-logs YAML configs as artifacts** (per-run versioning by design)
  - **dataset tracking** via `mlflow.log_input(...)`
  - **dataset fingerprinting** (hash + metadata) logged as artifacts/params/tags
- **Experiment Versioning**
  - auto-increments experiment folder suffix (e.g., `fault_detection_0`, `fault_detection_1`, ...)
  - sets MLflow tag `version = vX.0.0`
- **Git Traceability**
  - logs `commit_hash` (short) as an MLflow tag when available
- **Pluggable Tasks**
  - tasks are discovered automatically (`tasks/**/task.py`)
  - registry-based loading (no runner changes needed)
- **Pluggable Models**
  - users can implement custom models by inheriting from `BaseMLModel`
  - select the model in YAML (no code changes in training task)

---

## Pipeline Stages

1. **Load Dataset** (`load_ds`)
2. **EDA Checkpoint** (`eda_ds`)
3. **Preprocess** (`preprocess_ds`)
4. **Dimensionality Reduction** (`dim_reduction`)
5. **Training** (`training`)
6. **Hyperparameter Tuning** (`tuning`)

EDA can appear multiple times in `task_order` to act as checkpoints.

## Quickstart

### 1) Run the pipeline

Default config path is `configs`:

```bash
python main.py --config configs
```

### 2) View MLflow UI

MLflow uses local file-based tracking (`./mlruns`):

```bash
mlflow ui --backend-store-uri ./mlruns
```

## Configuration

### Master execution plan

`configs/master_config.yaml`:

```yaml
task_order:
  - task_eda.yaml
  - task_preprocess.yaml
  - task_eda.yaml
  - task_dim_reduction.yaml
  - task_eda.yaml
  - task_training.yaml
  - task_tuning.yaml
```

Repeating `task_eda.yaml` means EDA runs as checkpoints between transformations.

### Task configs

All task configs live under:

```
configs/tasks/*.yaml
```

Each config must contain:

```yaml
task_name: <registered_task_name>
```

## Reproducibility & Traceability

This pipeline is designed so a single MLflow run contains everything needed to reproduce results:

### Config Versioning (per run)

Each task YAML config is logged to MLflow as an artifact automatically.

### Experiment Version Tagging

Experiments auto-increment with suffixes (`<exp>_0`, `<exp>_1`, ...).
The pipeline sets:

- MLflow tag: `version = vX.0.0`

### Git Commit Tracking

If the project is inside a Git repository, the pipeline logs:

- MLflow tag: `commit_hash = <short_hash>`

This ties every run back to a specific code revision.

### Dataset Lineage + Fingerprinting

The dataset is tracked in two complementary ways:

1. **MLflow Dataset Tracking**
   - `mlflow.data.from_pandas(...)`
   - `mlflow.log_input(dataset)`

2. **Dataset Fingerprint Artifact**
   - lightweight JSON artifact: `dataset_fingerprint.json`
   - includes file size, modified time, rows/cols, target column, and a partial SHA256

This avoids uploading large datasets while still guaranteeing dataset identity.

**Logged to MLflow:**

- params:
  - `dataset.rows`, `dataset.columns`, `dataset.target`, `dataset.name`

- tag:
  - `dataset.hash = <partial_sha256>`

- artifact:
  - `dataset_fingerprint.json`

## Extensibility

### Add a new Task

1. Create `tasks/.../task_<your_task>/task.py`
2. Register:

```python
from core.task_registry import register_task
from core.base_task import BaseTask

@register_task("my_task")
class MyTask(BaseTask):
    ...
```

3. Add a YAML config and include it in `master_config.yaml`.

No runner changes needed.

---

### Add a new Model

1. Add a new model file under `models/`:

- file: `my_custom_model.py`
- class: `MyCustomModel(BaseMLModel)` (PascalCase)

2. Select it in `task_training.yaml`:

```yaml
task_name: training
model_type: pytorch
model_file_name: my_custom_model
model_params: {}
train_params: {}
```

The training task loads models dynamically via `importlib`.

## MLflow Outputs

Each run logs:

- **Params**
  - preprocessing & training params
  - tuning params (`tune_*`)
  - dataset summary fields

- **Metrics**
  - accuracy / precision / recall / f1
  - inference latency stats (mean / p95 / max)
  - EDA summary metrics

- **Artifacts**
  - EDA HTML reports (Plotly)
  - dim-reduction visualizations
  - training curves
  - confusion matrix + per-class metrics
  - dataset fingerprint JSON
  - YAML configs

- **Models**
  - trained and tuned models logged to MLflow with signatures

---

## Notes & Limitations

- Current pipeline targets **tabular classification** workflows.
- Dataset upload is intentionally avoided for large files; fingerprinting is used instead.
- Some config fields exist for future extensions (e.g., advanced solver options).
